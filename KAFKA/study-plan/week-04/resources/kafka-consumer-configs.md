# Apache Kafka 4.3 — Consumer Configs + Group Configs

> **Nguồn (official):** https://kafka.apache.org/43/configuration/consumer-configs/ (bản generated: https://kafka.apache.org/43/generated/consumer_config.html) · https://kafka.apache.org/43/configuration/group-configs/
> **Tuần:** 4 — Consumer chuyên sâu: group, rebalance, offset · **Loại:** Apache Kafka Docs
> ⚠️ Nội dung dưới đây được crawl tự động (qua WebFetch, có rút gọn — chỉ giữ các config hay bị hỏi) — luôn đối chiếu link gốc để đầy đủ & cập nhật nhất.

## 🎯 Điểm thi quan trọng (tóm tắt tiếng Việt)

- **Hai đồng hồ sống:** `session.timeout.ms` **45000** + `heartbeat.interval.ms` **3000** (heartbeat thread, chỉ với `group.protocol=classic`) và `max.poll.interval.ms` **300000** (processing thread). Đề cũ ghi session 10 s — đã đổi từ Kafka 3.0.
- `max.poll.records` **500** chỉ giới hạn số record **1 lần `poll()` trả về cho ứng dụng**, không đổi kích thước fetch request.
- Fetch: `fetch.min.bytes` **1** · `fetch.max.wait.ms` **500** · `fetch.max.bytes` **52428800** (50 MB) · `max.partition.fetch.bytes` **1048576** (1 MB). Tăng `fetch.min.bytes` + `fetch.max.wait.ms` để giảm số fetch request nhỏ.
- Offset: `enable.auto.commit` **true** · `auto.commit.interval.ms` **5000** · `auto.offset.reset` **latest** (earliest / none / `by_duration:PnDTnHnMn.nS`) — chỉ áp dụng khi **không có committed offset** hoặc offset out of range.
- Protocol: `group.protocol` **classic** (giá trị khác: `consumer` = KIP-848) · `group.remote.assignor` (null → broker dùng mặc định `uniform`) · `partition.assignment.strategy` mặc định **`[RangeAssignor, CooperativeStickyAssignor]`** (chỉ classic).
- `group.instance.id` (static membership, KIP-345) · `isolation.level` **read_uncommitted** · `client.rack` (follower fetching KIP-392, khớp `broker.rack`).
- **Group configs phía broker** (đặt bằng `kafka-configs.sh --entity-type groups`): `consumer.session.timeout.ms` **45000**, `consumer.heartbeat.interval.ms` **5000** (dùng cho `group.protocol=consumer`, thay cho client config).
- Share group configs: `share.record.lock.duration.ms` **30000**, `share.delivery.count.limit` **5**, `share.auto.offset.reset` **latest**, `share.isolation.level` **read_uncommitted**, `share.session.timeout.ms` 45000, `share.heartbeat.interval.ms` 5000.
- `request.timeout.ms` **30000**, `default.api.timeout.ms` **60000**, `allow.auto.create.topics` **true** (chỉ có hiệu lực khi broker `auto.create.topics.enable=true`).

## 📄 Nội dung (trích từ tài liệu gốc)

### Consumer Configs (selected)

| Config | Description | Type | Default | Valid Values | Importance |
|--------|-------------|------|---------|--------------|-----------|
| **bootstrap.servers** | A list of host/port pairs used to establish the initial connection to the Kafka cluster. Format `host1:port1,host2:port2,...` | list | — | — | high |
| **group.id** | A unique string that identifies the consumer group this consumer belongs to. Required if the consumer uses either the group management functionality by using `subscribe(topic)` or the Kafka-based offset management strategy. | string | null | — | high |
| **group.protocol** | The group protocol consumer should use. Supports `classic` or `consumer`. If `consumer` is specified, then the consumer group protocol (KIP-848) will be used. | string | classic | [CONSUMER, CLASSIC] | high |
| **group.remote.assignor** | The server-side assignor to use. If no assignor is specified, the group coordinator will pick one. This configuration is applied only if `group.protocol` is set to `consumer`. | string | null | — | medium |
| **group.instance.id** | A unique identifier of the consumer instance provided by the end user. Only non-empty strings are permitted. If set, the consumer is treated as a static member, which means that only one instance with this ID is allowed in the consumer group at any time. This can be used in combination with a larger session timeout to avoid group rebalances caused by transient unavailability (e.g. process restarts). If not set, the consumer will join the group as a dynamic member, which is the traditional behavior. | string | null | non-empty string | medium |
| **partition.assignment.strategy** | A list of class names or class types, ordered by preference, of supported partition assignment strategies that the client will use to distribute partition ownership amongst consumer instances when group management is used. Available options: `RangeAssignor`, `RoundRobinAssignor`, `StickyAssignor`, `CooperativeStickyAssignor`. The default assignor is `[RangeAssignor, CooperativeStickyAssignor]`, which will use the RangeAssignor by default, but allows upgrading to the CooperativeStickyAssignor with just a single rolling bounce that removes the RangeAssignor from the list. Only applies with `group.protocol=classic`. | list | RangeAssignor, CooperativeStickyAssignor | non-null string | medium |
| **session.timeout.ms** | The timeout used to detect client failures when using Kafka's group management facility. The client sends periodic heartbeats to indicate its liveness to the broker. If no heartbeats are received by the broker before the expiration of this session timeout, then the broker will remove this client from the group and initiate a rebalance. The value must be in the allowable range as configured in the broker configuration by `group.min.session.timeout.ms` and `group.max.session.timeout.ms`. Only supported with `group.protocol=classic`. | int | 45000 (45 seconds) | — | high |
| **heartbeat.interval.ms** | The expected time between heartbeats to the consumer coordinator when using Kafka's group management facilities. Heartbeats are used to ensure that the consumer's session stays active and to facilitate rebalancing when new consumers join or leave the group. The value must be set lower than `session.timeout.ms`, but typically should be set no higher than 1/3 of that value. Only supported with `group.protocol=classic`. | int | 3000 (3 seconds) | — | high |
| **max.poll.interval.ms** | The maximum delay between invocations of `poll()` when using consumer group management. This places an upper bound on the amount of time that the consumer can be idle before fetching more records. If `poll()` is not called before expiration of this timeout, then the consumer is considered failed and the group will rebalance in order to reassign the partitions to another member. For consumers using a non-null `group.instance.id` which reach this timeout, partitions will not be immediately reassigned; instead the consumer will stop sending heartbeats and partitions will be reassigned after expiration of `session.timeout.ms`. | int | 300000 (5 minutes) | [1,...] | medium |
| **max.poll.records** | The maximum number of records returned in a single call to `poll()`. Note that `max.poll.records` does not impact the underlying fetching behavior. The consumer will cache the records from each fetch request and returns them incrementally from each poll. | int | 500 | [1,...] | medium |
| **enable.auto.commit** | If true the consumer's offset will be periodically committed in the background. | boolean | true | — | medium |
| **auto.commit.interval.ms** | The frequency in milliseconds that the consumer offsets are auto-committed to Kafka if `enable.auto.commit` is set to true. | int | 5000 (5 seconds) | [0,...] | low |
| **auto.offset.reset** | What to do when there is no initial offset in Kafka or if the current offset does not exist any more on the server (e.g. because that data has been deleted): `earliest` — automatically reset the offset to the earliest offset; `latest` — automatically reset the offset to the latest offset; `by_duration:<duration>` — reset to a configured duration from the current timestamp (ISO8601, e.g. `PT10H`); `none` — throw exception to the consumer if no previous offset is found for the consumer's group; anything else — throw exception. | string | latest | [latest, earliest, none, by_duration:PnDTnHnMn.nS] | medium |
| **isolation.level** | Controls how to read messages written transactionally. If set to `read_committed`, `consumer.poll()` will only return transactional messages which have been committed. If set to `read_uncommitted` (the default), `consumer.poll()` will return all messages, even transactional messages which have been aborted. Non-transactional messages will be returned unconditionally in either mode. Messages will always be returned in offset order. In `read_committed` mode the consumer can only read up to the last stable offset (LSO), which is the one less than the offset of the first open transaction. | string | read_uncommitted | [read_committed, read_uncommitted] | medium |
| **fetch.min.bytes** | The minimum amount of data the server should return for a fetch request. If insufficient data is available the request will wait for that much data to accumulate before answering the request. Setting this to a larger value will cause the server to wait for larger amounts of data to accumulate which can improve server throughput a bit at the cost of some additional latency. | int | 1 | [0,...] | high |
| **fetch.max.wait.ms** | The maximum amount of time the server will block before answering the fetch request there isn't sufficient data to immediately satisfy the requirement given by `fetch.min.bytes`. | int | 500 | [0,...] | low |
| **fetch.max.bytes** | The maximum amount of data the server should return for a fetch request. Records are fetched in batches by the consumer, and if the first record batch in the first non-empty partition of the fetch is larger than this value, the record batch will still be returned to ensure that the consumer can make progress. As such, this is not an absolute maximum. | int | 52428800 (50 mebibytes) | [0,...] | medium |
| **max.partition.fetch.bytes** | The maximum amount of data per-partition the server will return. If the first record batch in the first non-empty partition of the fetch is larger than this limit, the batch will still be returned to ensure that the consumer can make progress. The maximum record batch size accepted by the broker is defined via `message.max.bytes` (broker config) or `max.message.bytes` (topic config). | int | 1048576 (1 mebibyte) | [0,...] | high |
| **client.rack** | A rack identifier for this client. This can be any string value which indicates where this client is physically located. It corresponds with the broker config `broker.rack`. | string | "" | — | low |
| **allow.auto.create.topics** | Allow automatic topic creation on the broker when subscribing to or assigning a topic. A topic being subscribed to will be automatically created only if the broker allows for it using `auto.create.topics.enable` broker configuration. | boolean | true | — | medium |
| **request.timeout.ms** | The configuration controls the maximum amount of time the client will wait for the response of a request. If the response is not received before the timeout elapses the client will resend the request if necessary or fail the request if retries are exhausted. | int | 30000 (30 seconds) | [0,...] | medium |
| **default.api.timeout.ms** | Specifies the timeout (in milliseconds) for client APIs. This configuration is used as the default timeout for all client operations that do not specify a `timeout` parameter. | int | 60000 (1 minute) | [0,...] | medium |
| **share.acknowledgement.mode** | Controls the acknowledgement mode for a share consumer. If set to `implicit`, the acknowledgement mode of the consumer is implicit and it must not use `KafkaShareConsumer.acknowledge()` to acknowledge delivery of records. Instead, delivery is acknowledged implicitly on the next call to poll or commit. If set to `explicit`, the acknowledgement mode of the consumer is explicit and it must use `KafkaShareConsumer.acknowledge()` to acknowledge delivery of records. | string | implicit | [implicit, explicit] | medium |

### Group Configs (broker-side, per group — `kafka-configs.sh --entity-type groups --entity-name <group>`)

| Configuration | Description | Type | Default | Valid Values | Importance |
|---|---|---|---|---|---|
| `consumer.assignment.interval.ms` | The interval between assignment updates for a consumer group. | int | 1000 (1 second) | [0,...] | medium |
| `consumer.heartbeat.interval.ms` | The heartbeat interval given to the members of a consumer group. | int | 5000 (5 seconds) | [1,...] | medium |
| `consumer.session.timeout.ms` | The timeout to detect client failures when using the consumer group protocol. | int | 45000 (45 seconds) | [1,...] | medium |
| `share.assignment.interval.ms` | The interval between assignment updates for a share group. | int | 1000 (1 second) | [0,...] | medium |
| `share.heartbeat.interval.ms` | The heartbeat interval given to the members of a share group. | int | 5000 (5 seconds) | [1,...] | medium |
| `share.session.timeout.ms` | The timeout to detect client failures when using the share group protocol. | int | 45000 (45 seconds) | [1,...] | medium |
| `share.record.lock.duration.ms` | The record acquisition lock duration in milliseconds for share groups. | int | 30000 (30 seconds) | [1000,...] | medium |
| `share.auto.offset.reset` | The strategy to initialize the share-partition start offset: `earliest`, `latest`, or `by_duration:<ISO8601 duration>`. | string | latest | latest, earliest, by_duration | medium |
| `share.isolation.level` | Controls how to read records written transactionally: `read_committed` or `read_uncommitted`. | string | read_uncommitted | read_committed, read_uncommitted | medium |
| `share.delivery.count.limit` | The maximum number of delivery attempts for a record delivered to a share group. | int | 5 | [2,...] | medium |
| `share.partition.max.record.locks` | Share-group record lock limit per share-partition. | int | 2000 | [100,...] | medium |
| `share.renew.acknowledge.enable` | Enables the RENEW acknowledge type for the share group (KIP-1222). | boolean | true | — | medium |
| `streams.heartbeat.interval.ms` | The heartbeat interval given to the members of a streams group. | int | 5000 (5 seconds) | [1,...] | medium |
| `streams.session.timeout.ms` | The timeout to detect client failures when using the streams group protocol. | int | 45000 (45 seconds) | [1,...] | medium |
| `streams.initial.rebalance.delay.ms` | The amount of time the group coordinator will wait for more consumers to join a new group before performing the first rebalance. | int | 3000 (3 seconds) | [0,...] | medium |
| `streams.num.standby.replicas` | The number of standby replicas for each task. | int | 0 | [0,...] | medium |

> Note: with `group.protocol=consumer` (KIP-848) the client-side `session.timeout.ms`, `heartbeat.interval.ms` and `partition.assignment.strategy` are not used; the group coordinator applies `consumer.session.timeout.ms` / `consumer.heartbeat.interval.ms` from the group configuration (bounded by broker `group.consumer.min/max.session.timeout.ms` and `group.consumer.min/max.heartbeat.interval.ms`).

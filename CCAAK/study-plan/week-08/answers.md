### Question 1 — Answer: **B**

- **Why correct:** node **4 is absent from every single ISR** while nodes 2 and 3 appear everywhere. That pattern is a statement about one broker, not about replication tuning. The first move is free and reversible: confirm whether broker 4 is running, whether its disk is healthy, and what `server.log` says. Producers still succeeding confirms the ISR is still at 2, which equals `min.insync.replicas` — there is no data-loss emergency yet, so there is time to diagnose properly.
- **Why the others are wrong:** **A** — unclean leader election trades data for availability, and nothing here is even unavailable; it is the most expensive, least reversible action on the list. **C** — lowering `min.insync.replicas` to 1 makes the alarm disappear without fixing anything and removes the last guard against silent data loss; it is the textbook "panic change". **D** — reassigning every replica off broker 4 copies terabytes across the cluster to work around a broker that may simply need restarting; reassignment is the remedy for a *permanently* removed broker, not for a broker that has been down four minutes.
- 🧠 **Key point / trap:** `UnderReplicatedPartitions` > 0 means **redundancy is degraded**, not that service is lost. Read the ISR lists to find the *missing node id* before touching any config — the identity of the missing replica is the diagnosis.

### Question 2 — Answer: **C**

- **Why correct:** Kafka resolves a configuration through five levels and the **most specific wins**: `DYNAMIC_TOPIC_CONFIG` > `DYNAMIC_BROKER_CONFIG` > `DYNAMIC_DEFAULT_BROKER_CONFIG` > `STATIC_BROKER_CONFIG` > `DEFAULT_CONFIG`. The `--describe --all` output says it outright by listing `DYNAMIC_TOPIC_CONFIG` first in the synonyms. A cluster-wide default never overrides a topic that already has its own value; the topic override must be changed or deleted.
- **Why the others are wrong:** **A** — dynamic default broker configs apply immediately to running brokers; that is the whole point of `kafka-configs.sh`. **B** — `min.insync.replicas` is very much dynamically alterable at broker and topic level; had it been read-only the command would have been rejected, not silently ignored. **D** — a **version trap**: there are no znodes in Kafka 4.x, `zookeeper-shell.sh` no longer applies to broker configuration, and dynamic configs live in `__cluster_metadata`.
- 🧠 **Key point / trap:** whenever a config "does not take effect", run `--describe --all` and **read the synonyms column** — it tells you exactly which level is winning. This is also the reason `min.insync.replicas` set at broker level is a classic exam trap.

### Question 3 — Answer: **A**

- **Why correct:** the log line names everything needed: principal `User:orders-svc`, operation `Read`, resource `Group:LITERAL:fulfillment`, request `OffsetFetch`. A consumer needs **two** ACLs — `Read` on the Topic **and** `Read` on the Group — and only the Group one is missing, which is exactly why producing still works. Granting `Read` on that one group is the minimum change.
- **Why the others are wrong:** **B** — `super.users` bypasses **all** authorization for that principal, a massive privilege escalation to fix one missing grant, and it needs a broker restart. **C** — `allow.everyone.if.no.acl.found=true` disables the default-deny posture for the **entire cluster**; it turns a one-ACL problem into a security incident. **D** — a **version trap**: `AclAuthorizer` was the ZooKeeper-era authorizer and was removed in Kafka 4.0; KRaft uses `StandardAuthorizer`, which evaluates Group ACLs perfectly well.
- 🧠 **Key point / trap:** `TopicAuthorizationException` → missing Topic ACL; `GroupAuthorizationException` (or a denied `OffsetFetch` on a Group resource) → missing **Group** ACL. `kafka-authorizer.log` prints the exact resource — read it instead of guessing.

### Question 4 — Answer: **A, C**

- **Why correct:** **A** — `broker.rack` is what tells the controller that brokers belong to different failure domains; with it set, replica placement spreads the replicas of each partition across racks, so losing one AZ costs at most one replica per partition instead of all three. **C** — follower fetching (KIP-392) with `client.rack` lets a consumer read from the replica in its own rack rather than always from the leader, which is precisely the cross-AZ transfer cost the team wants to cut.
- **Why the others are wrong:** **B** — `min.insync.replicas=3` with RF 3 does not improve placement at all, and it makes the cluster **less** available: losing any single broker stops writes. **D** — `num.replica.fetchers` controls how many fetcher threads a broker uses to catch up; it has nothing to do with where replicas are placed or where consumers read from. **E** — unclean leader election allows a lagging replica to become leader and **lose acknowledged data**; it addresses neither placement nor cost.
- 🧠 **Key point / trap:** rack awareness is a **placement** feature (`broker.rack`, applied when partitions are created or reassigned) and follower fetching is a **read-path** feature (`client.rack`). Setting `broker.rack` on an existing cluster does **not** retroactively move replicas — you still have to reassign.
- 📎 Source: [§4 Domain 5 — Deployment Architecture](../../CCAAK-STUDY-PLAN.md#4-kiến-thức-theo-domain) · [`resources/ccaak-vs-ccdak-map.md`](resources/ccaak-vs-ccdak-map.md)

### Question 5 — Answer: **D**

- **Why correct:** the three numbers point at exactly one pool. `RequestHandlerAvgIdlePercent` at **0.08** is far below the healthy floor of **0.3**, meaning the request handler (I/O) threads are busy 92% of the time. `NetworkProcessorAvgIdlePercent` at 0.65 says the network threads are fine. `TotalTimeMs` being dominated by `RequestQueueTimeMs` says requests are waiting to be *picked up*, not waiting on disk or on followers. `num.io.threads` (default **8**) is the dial for that pool, it is dynamic, per-broker, and trivially reversible.
- **Why the others are wrong:** **A** — the network processors are 65% idle; adding threads to an idle pool does nothing. **B** — `queued.max.requests` only makes the queue **longer**, which increases latency further; it does not add capacity to drain it. **C** — adding brokers is the most expensive and slowest option, and would be premature while a single dynamic config change is untested; CPU at 40% shows the host has headroom.
- 🧠 **Key point / trap:** learn the pair — `RequestHandlerAvgIdlePercent` → `num.io.threads`; `NetworkProcessorAvgIdlePercent` → `num.network.threads`. The idle metric that is **low** names the pool to grow.

### Question 6 — Answer: **A**

- **Why correct:** Kafka deletes whole **segments**, and the **active** segment is never deleted. At 8 MB/day the active segment needs roughly 350 years to reach `segment.bytes` of 1 GiB, and `log.roll.hours` of 168 means it only rolls once a week. Nothing becomes eligible for deletion within the hour, so `retention.ms=3600000` appears to do nothing. Lowering `segment.ms` (or `segment.bytes`) on the topic makes segments roll and retention effective.
- **Why the others are wrong:** **B** — a topic-level `retention.ms` legitimately overrides the broker default in both directions; there is no floor at 168 hours. **C** — `log.retention.check.interval.ms` is how often the broker *looks* for expired segments; five minutes cannot explain five days, and lowering it to 1 s just burns CPU. **D** — the `delete` policy is fully automatic; the log **cleaner** is the compaction thread and is a different mechanism entirely.
- 🧠 **Key point / trap:** *"retention is set but the data is still there"* is a **segment-roll** question, never a retention question. This is also why every retention lab sets `segment.ms` to a few seconds.
- 📎 Source: [§7 bảng phản xạ](../../CCAAK-STUDY-PLAN.md#7-bảng-phản-xạ-triệu-chứng--hành-động) · [`../../../CCDAK/study-plan/week-02/resources/kafka-topic-configs.md`](../../../CCDAK/study-plan/week-02/resources/kafka-topic-configs.md)

### Question 7 — Answer: **B**

- **Why correct:** in Kafka Connect the **connector** object and its **tasks** have independent states. A connector can sit at `RUNNING` while every one of its tasks is `FAILED` — which is exactly why monitoring that only watches `connector.state` misses outages. The task is restarted through the REST API (`/tasks/1/restart`, or `restart?includeTasks=true` for the whole connector), and because the cause is a record that fails conversion, the durable fix is `errors.tolerance=all` **plus** a dead letter queue so the poison record is routed aside instead of killing the task again on the next attempt.
- **Why the others are wrong:** **A** — deleting and recreating loses the connector's committed state for no reason; a `DataException` on one record says nothing about the configuration. **C** — Connect does **not** automatically restart failed tasks; `task.shutdown.graceful.timeout.ms` bounds how long a task is given to stop, it is not a retry timer. **D** — `tasks.max` is an upper bound on how many tasks may be created; it never makes one task absorb another's partitions, and a failed task's partitions are simply not consumed.
- 🧠 **Key point / trap:** alert on **task** state, not connector state. And remember the DLQ rule: `errors.deadletterqueue.topic.name` works on **sink** connectors only, and `errors.tolerance=all` *without* a DLQ silently drops the record.
- 📎 Source: [`../../../CCDAK/study-plan/week-05/resources/connect-error-handling-dlq-kip298.md`](../../../CCDAK/study-plan/week-05/resources/connect-error-handling-dlq-kip298.md) · [`../../../CCDAK/study-plan/week-05/resources/connect-user-guide-configs-rest.md`](../../../CCDAK/study-plan/week-05/resources/connect-user-guide-configs-rest.md)

### Question 8 — Answer: **C**

- **Why correct:** in KRaft the controllers form a **Raft quorum** over the internal metadata log `__cluster_metadata`. When the leader dies, the remaining voters run an election and one of them becomes the new active controller — a few seconds, after which `ActiveControllerCount` summed across the cluster is 1 again. Brokers cache metadata and keep serving produce and fetch requests during the gap; only metadata *changes* (topic creation, leader election, config updates) pause.
- **Why the others are wrong:** **A** — a **version trap**, and the single most dangerous one in public CCAAK dumps, where this is often marked as the correct answer. ZooKeeper and its `/controller` ephemeral node were removed in Kafka 4.0. **B** — brokers do not go read-only during a controller election; that is exactly the availability property the quorum provides. **D** — another ZooKeeper-era fiction: `zookeeper.connect` no longer exists, and controller leadership is decided by Raft, not by node id ordering.
- 🧠 **Key point / trap:** with a quorum of 3 you survive the loss of `(3−1)/2 = 1` controller; with 5, two. When `ActiveControllerCount` misbehaves, the diagnostic command is `kafka-metadata-quorum.sh describe --status`.
- 📎 Source: [§6 KRaft](../../CCAAK-STUDY-PLAN.md#6-những-con-số-phải-thuộc-lòng) · [`resources/kafka-4x-operational-changes.md`](resources/kafka-4x-operational-changes.md) · [`../VALIDATION.md`](../VALIDATION.md)

### Question 9 — Answer: **B, D**

- **Why correct:** **B** — Kafka quotas are enforced by **delaying the response** to the client for as long as needed to bring the observed rate back under the limit. Nothing is rejected, so nothing is logged as an error on either side; the only visible trace is the throttle-time metric. **D** — a byte-rate ceiling on a producer is `producer_byte_rate`, and quota configuration is resolved through **8 levels of precedence**, starting at the most specific (user + client-id) and falling back to the cluster-wide default.
- **Why the others are wrong:** **A** — buffer exhaustion produces a very different signature: a `TimeoutException` about allocating memory, and `buffer-available-bytes` near zero. It also would not pin throughput to a suspiciously round 10 MB/s. **C** — there is no exception delivered to the client for a quota breach; that is the entire point of throttling by delay. **E** — quotas are dynamic configuration managed with `kafka-configs.sh` on user/client-id entities and take effect without a restart.
- 🧠 **Key point / trap:** *"throughput is pinned to a flat ceiling and the logs are clean"* is the signature of a **quota**, not of a bug. Check `produce-throttle-time-avg` / `fetch-throttle-time-avg` before chasing anything else.
- 📎 Source: [§4 Domain 1 — quotas](../../CCAAK-STUDY-PLAN.md#4-kiến-thức-theo-domain) · [`../../../CCDAK/study-plan/week-07/resources/kafka-quotas.md`](../../../CCDAK/study-plan/week-07/resources/kafka-quotas.md)

### Question 10 — Answer: **A**

- **Why correct:** the log shows JBOD behaving as designed — one `log.dirs` entry failed (out of space), the broker stopped serving **that directory only**, and partitions hosted there now throw `KafkaStorageException` while the rest of the broker keeps working. `kafka-log-dirs.sh --describe --broker-list 3` is the free, read-only command that tells you which partitions were on the dead directory and how much room the survivor has — the facts you need before choosing a remedy.
- **Why the others are wrong:** **B** — restarting does not create disk space, and on restart the broker must recover logs on the remaining directory, adding downtime for no benefit. **C** — the partitions are offline because their **storage** is gone, not because no in-sync replica exists elsewhere; unclean election is unrelated here and risks data loss. **D** — deleting segment files by hand under a running broker corrupts the log; Kafka manages its own segments, and the index files would be left inconsistent.
- 🧠 **Key point / trap:** a failed `log.dirs` entry takes only its own partitions down — the broker dies only when **all** directories fail. Kafka 4.3 adds **cordoning** (KIP-1066) so the controller stops placing new partitions on a directory you are retiring.

### Question 11 — Answer: **C**

- **Why correct:** every pairing matches the layer that actually failed. `TopicAuthorizationException` = **authorization**, no matching ACL on the Topic resource. `GroupAuthorizationException` = **authorization**, missing `Read` on the Group resource (the reason a consumer needs two ACLs). `SaslAuthenticationException` = **authentication**, the credential was rejected before any authorization happened. `SSLHandshakeException` = **transport**, the TLS handshake never completed — an untrusted or expired certificate, or a missing client certificate under mTLS.
- **Why the others are wrong:** **A** — swaps the two authorization exceptions and swaps the SASL/SSL causes; each half is plausible on its own, which is exactly how matching questions punish partial knowledge. **B** — a missing topic yields `UnknownTopicOrPartitionException`, a rebalancing group yields `RebalanceInProgressException`; neither is an authorization exception, and `ssl.client.auth=none` makes the handshake *more* permissive, not less. **D** — collapses three different layers (transport, authentication, authorization) into one, which is precisely the distinction the exam is testing.
- 🧠 **Key point / trap:** map every security error to one of three layers first — **encryption (TLS) → authentication (SASL/mTLS) → authorization (ACL)** — then fix at that layer. Adding ACLs never fixes a handshake failure.
- 📎 Source: [`../../../CCDAK/study-plan/week-07/resources/kafka-security-overview.md`](../../../CCDAK/study-plan/week-07/resources/kafka-security-overview.md) · [`../../../CCDAK/study-plan/week-07/resources/kafka-security-ssl.md`](../../../CCDAK/study-plan/week-07/resources/kafka-security-ssl.md)

### Question 12 — Answer: **B**

- **Why correct:** Cluster Linking is a **broker-level** replication feature of Confluent Platform: the destination broker fetches partitions directly from the source and writes them at the **same offsets**, byte for byte. Consumers that fail over therefore resume exactly where they stopped, with no offset translation step — and there is no Connect cluster to size, monitor or upgrade, which satisfies "fewest moving parts". The company already runs Confluent Platform, so the feature is available.
- **Why the others are wrong:** **A** — `IdentityReplicationPolicy` only stops MM2 from prefixing the topic name with the source cluster alias; it changes **naming**, not offsets. MM2 always writes into a fresh log on the target, so offsets differ and must be translated through checkpoints. **C** — a **version trap**: MirrorMaker 1 was removed in Kafka 4.0 and never had offset translation in the first place. **D** — a stretch cluster does give RPO 0 without any replication tool, but it requires low latency between the sites and turns two independent failure domains into one quorum; it is a different architecture, not a DR tool, and the scenario describes two separate clusters.
- 🧠 **Key point / trap:** the one-line rule — **MM2 changes offsets and needs translation; Cluster Linking preserves them.** When a question says "same offsets after failover" on Confluent Platform, the answer is Cluster Linking.
- 📎 Source: [§5 Disaster recovery](../../CCAAK-STUDY-PLAN.md#5-deep-dive-từng-mảng-vận-hành) · [`../../../CCDAK/study-plan/week-08/resources/kafka-georeplication-mirrormaker2.md`](../../../CCDAK/study-plan/week-08/resources/kafka-georeplication-mirrormaker2.md)

### Question 13 — Answer: **A**

- **Why correct:** the recovering broker is nowhere near any hardware limit — NIC 15%, disks quiet, CPU 20% — yet catch-up is crawling. That combination means the broker is **not fetching in parallel enough**: `num.replica.fetchers` defaults to **1**, i.e. one fetcher thread per source broker. Raising it is a dynamic per-broker config, needs no restart, uses the headroom that is visibly available, and can be set back to 1 once the ISR is whole.
- **Why the others are wrong:** **B** — raising `replica.lag.time.max.ms` makes lagging replicas *count* as in-sync sooner; it silences `UnderReplicatedPartitions` without copying a single extra byte, and it weakens the durability guarantee of `acks=all`. **C** — unclean election is for partitions with **no** in-sync replica; here the replicas exist and are catching up, and forcing leadership onto the lagging broker would lose data. **D** — `num.io.threads` sizes the request handler pool for client requests; replication fetches are issued by the fetcher threads, so this is the wrong dial.
- 🧠 **Key point / trap:** "URP not coming down and the hardware is idle" → `num.replica.fetchers`. "URP not coming down and the NIC is saturated" → you are bandwidth-bound; throttle other traffic instead. Never fix URP by loosening `replica.lag.time.max.ms`.

### Question 14 — Answer: **A, D**

- **Why correct:** **A** — every partition that had a replica on the dead broker now has fewer in-sync replicas than replicas, so the surviving leaders report `UnderReplicatedPartitions` > 0. That is the expected, correct signal. **D** — with RF 3 and `min.insync.replicas=2`, two replicas remain in sync, which still satisfies the minimum, so `UnderMinIsrPartitionCount` stays 0 and `acks=all` producers are unaffected. This is exactly the property the RF 3 / min.isr 2 / `acks=all` triple is chosen for.
- **Why the others are wrong:** **B** — one controller remains active; the cluster-wide sum of `ActiveControllerCount` stays at 1 unless the controller quorum itself loses majority (and with dedicated controllers, a broker crash does not touch the quorum). **C** — a partition only goes offline when it has **no** in-sync replica left; with RF 3 and one broker down, two replicas remain, so `OfflinePartitionsCount` stays 0. **E** — `records-lag-max` is a **consumer client** metric; brokers do not track consumer lag internally, which is why lag monitoring uses `kafka-consumer-groups.sh` or a lag exporter.
- 🧠 **Key point / trap:** learn the severity ladder — `UnderReplicatedPartitions` = degraded redundancy (ticket), `UnderMinIsrPartitionCount` = writes blocked (page), `OfflinePartitionsCount` = availability lost (page immediately).

### Question 15 — Answer: **C**

- **Why correct:** `min.insync.replicas=3` on an RF 3 topic is the classic **over-correction**: it looks maximally durable but it means the topic cannot tolerate the loss of a single replica, so any maintenance stops writes with `NotEnoughReplicasException`. Setting it to **2** restores writes immediately and keeps the real guarantee: an `acks=all` write is only acknowledged once **two** replicas hold it, so losing one broker loses nothing.
- **Why the others are wrong:** **A** — `min.insync.replicas=1` means an `acks=all` write can be acknowledged by the leader alone, so a leader failure right after the ack loses acknowledged data; that is well below the production standard. **B** — `acks=1` has the same defect and, worse, it is a silent client-side change that nobody remembers to revert after the maintenance window. **D** — unclean leader election has nothing to do with this failure (there is no offline partition), and it permits data loss whenever it does fire.
- 🧠 **Key point / trap:** with RF 3 the durable answer is **always 2**. `min.isr = RF` converts a durability setting into an availability outage, and this exact scenario is the single most repeated question shape in CCAAK.

### Question 16 — Answer: **A, C**

- **Why correct:** **A** — a distributed worker persists all of its state in three compacted internal topics, created by default as `connect-configs` with **1** partition, `connect-offsets` with **25** and `connect-status` with **5**; a production cluster raises their replication factor to 3 because losing them loses every connector configuration. **C** — `tasks.max` is a **ceiling**, not a target: a sink connector cannot usefully create more tasks than the topic has partitions, so any surplus tasks are assigned nothing and idle, exactly like surplus consumers in a consumer group.
- **Why the others are wrong:** **B** — `connect-offsets` holds **source** connector offsets; a **sink** connector is an ordinary consumer group and commits to `__consumer_offsets`. **D** — a **version trap**: Connect workers coordinate through the Kafka group protocol using `group.id`, and `zookeeper.connect` does not exist in 4.x at all. **E** — in distributed mode connector configurations come from the REST API and are shared across the cluster through `connect-configs`; listing connectors per worker is **standalone** mode behaviour.
- 🧠 **Key point / trap:** memorise **1 / 25 / 5** and the sentence *"source offsets in `connect-offsets`, sink offsets in `__consumer_offsets`"*. Both appear regularly.

### Question 17 — Answer: **D**

- **Why correct:** this is the canonical four-step reassignment. `--generate` only **prints** two JSON documents (the current assignment, which you keep as your rollback plan, and the proposed one) — nothing moves yet. `--execute --throttle <bytes/s>` starts the move and writes dynamic throttle configs at broker level (`leader/follower.replication.throttled.rate`) and topic level (`*.replication.throttled.replicas`). `--verify` is polled until every partition reports `completed`, and **that same command is what clears the throttle configs**. Finally, leadership after a reassignment is usually not on the preferred replica, so `kafka-leader-election.sh --election-type preferred` puts it back.
- **Why the others are wrong:** **A** — `--execute` requires the JSON that `--generate` produces, so the order is impossible; and reassignment never needs a broker restart. **B** — a **version trap** on two counts: `--zookeeper` was removed, and adding partitions is a completely different operation that does not move existing replicas onto the new broker (it also breaks key-to-partition mapping). **C** — the trap that costs real clusters real money: throttles are **not** removed automatically. Skipping `--verify` leaves `leader.replication.throttled.rate` in place, quietly capping all future replication — including the recovery after the next broker failure.
- 🧠 **Key point / trap:** *"`--verify` is the step that removes the throttle."* Also remember that adding a broker never moves existing partitions: the new node only receives topics created afterwards until you reassign.

### Question 18 — Answer: **A**

- **Why correct:** in KRaft, SCRAM credentials are stored in the **cluster metadata log**, not in a per-broker file. Altering the user entity with `kafka-configs.sh` writes a metadata record that every broker applies immediately, so the new password is valid cluster-wide within seconds with no restart and no window. The old password stops working as soon as it is replaced, so the practical sequence is: add the new credential, roll the clients, verify, and only then retire the old one if you staged both.
- **Why the others are wrong:** **B** — `kafka_server_jaas.conf` holds the **broker's own** login configuration (and, in the old ZooKeeper world, static user definitions); editing it per broker plus a rolling restart is exactly the downtime the requirement forbids. **C** — `kafka-storage.sh format --add-scram` seeds a credential at **format** time, before the cluster exists; re-running format on a live broker would destroy its log directory. **D** — a **version trap**: there is no `/config/users` znode in Kafka 4.x and `zookeeper-shell.sh` has no cluster to talk to.
- 🧠 **Key point / trap:** "rotate a credential with no restart" → `kafka-configs.sh --entity-type users` (KRaft metadata). "Bootstrap the very first credential before the cluster starts" → `kafka-storage.sh format --add-scram`. Two different moments, two different tools.

### Question 19 — Answer: **B**

- **Why correct:** the client reaches the bootstrap listener, so the network path to *that* address works; but the bootstrap response hands back the **advertised** addresses of all brokers, and the client must connect to those to fetch topic metadata and produce. If `advertised.listeners` publishes an internal hostname (a container name, a private DNS record, a Docker network alias), a client in another subnet resolves nothing and times out waiting for metadata — while clients on the broker subnet work perfectly, which is precisely the asymmetry described.
- **Why the others are wrong:** **A** — the topic already exists, as verified from inside the container, so auto-creation is irrelevant. **C** — `metadata.max.age.ms` controls how often a client **refreshes** metadata it already has; a brand-new client always fetches metadata immediately. **D** — a broken controller quorum would affect every client, including the ones on the broker subnet that are working fine.
- 🧠 **Key point / trap:** *"connects to bootstrap but times out on metadata or produce"* is the signature of an `advertised.listeners` problem. `listeners` is where the broker **binds**; `advertised.listeners` is what it **tells clients to use** — they are not the same thing and the second one is what clients obey.

### Question 20 — Answer: **A**

- **Why correct:** the documented 4.0+ procedure has exactly three phases, and the order matters. First roll the nodes **one at a time** — controlled shutdown, swap binaries, start, and crucially **wait for `UnderReplicatedPartitions` to return to 0** before touching the next node, so the cluster never has two degraded brokers at once. Second, run the whole cluster on the new version long enough to be confident. Only then finalize with `kafka-features.sh upgrade --release-version 4.3`, which raises `metadata.version` and enables the new metadata features.
- **Why the others are wrong:** **B** — inverted and dangerous: finalizing first would raise the metadata version above what the not-yet-upgraded nodes can read. **C** — `inter.broker.protocol.version` was the ZooKeeper-era mechanism; in KRaft its role is taken by `metadata.version` managed through `kafka-features.sh`. Restarting all brokers simultaneously is a full outage, not a rolling upgrade. **D** — a **version trap**: there is no ZooKeeper to stop on a 4.2 cluster, and the ZK-to-KRaft migration is a pre-4.0 concern.
- 🧠 **Key point / trap:** finalizing is effectively **one-way** — 4.3.0 has metadata changes and therefore **no downgrade support** (4.2.0 was the exception). Run the new binaries for a few days *before* you finalize, not in the same maintenance window.

### Question 21 — Answer: **C**

- **Why correct:** Kafka's log-directory placement is deliberately simple: a new partition goes to the directory currently holding the **fewest partitions**. It does not consider free space or partition size, so a handful of high-volume partitions landing in the same directory produces exactly this skew even though partition *counts* are balanced. The cheap, in-broker remedy is an intra-broker move: `kafka-reassign-partitions.sh` accepts a `log_dirs` array alongside `replicas`, so specific replicas can be relocated between directories on the same broker without leaving the host. On 4.3 the directory can additionally be **cordoned** (KIP-1066) so nothing new is placed there while you drain it.
- **Why the others are wrong:** **A** — Kafka does not balance by free space, so the skew is expected behaviour rather than evidence of a hardware fault; the question states no directory has failed. **B** — moving partitions between directories inside one broker is precisely what the `log_dirs` field exists for; adding a broker is a far more expensive answer to a local problem. **D** — `log.retention.bytes` is a per-partition limit applied on every broker holding that partition, so it would delete data cluster-wide, not just on disk4, and it changes the data retention contract to fix a placement problem.
- 🧠 **Key point / trap:** "Kafka spreads by **partition count**, not by bytes" explains most JBOD imbalance questions. The same tool does inter-broker moves (`replicas`) and intra-broker moves (`log_dirs`).

### Question 22 — Answer: **B, C**

- **Why correct:** **B** — the ISR membership test is time-based: a follower that has not caught up within `replica.lag.time.max.ms` (**30000** ms) is dropped from the ISR and re-added once it catches up, which is the shrink/expand flapping being observed. **C** — `acks=all` waits only for the replicas **currently in the ISR**. This is why `min.insync.replicas` exists: without it, an ISR that has shrunk to one replica would still satisfy `acks=all` with a single copy.
- **Why the others are wrong:** **A** — the high watermark is the highest offset replicated to all replicas **in the ISR**, not to out-of-sync replicas; if it waited for out-of-sync replicas, a single lagging follower would stall all consumers. **D** — Kafka never auto-creates replacement replicas; the replica set changes only through an explicit reassignment. That misconception is why people are surprised that adding a broker does nothing. **E** — `replica.lag.max.messages` was the old message-count threshold and was removed years ago in favour of the time-based check; quoting it is an old-defaults trap.
- 🧠 **Key point / trap:** flapping ISR is almost always a **symptom** (long GC pauses, slow disks, network jitter), not a configuration problem. Investigate GC logs and disk latency — do not "fix" it by raising `replica.lag.time.max.ms`, which only hides it.

### Question 23 — Answer: **A, B**

- **Why correct:** **A** — a `PREFIXED` resource pattern matches every resource whose name starts with the prefix, evaluated at request time, so topics created later are covered automatically. That is exactly what makes prefix ACLs the standard tool for multi-tenant naming conventions. **B** — the authorizer's rule is unconditional: if any matching DENY exists, the request is denied, no matter how specific the ALLOW is or in what order they were added.
- **Why the others are wrong:** **C** — `super.users` bypasses authorization entirely for that principal across the whole cluster; it is the opposite of least privilege and cannot express "only `team-a.*`". **D** — with an authorizer configured, `allow.everyone.if.no.acl.found` defaults to **false**, i.e. default-deny; the option in the question inverts the security posture. **E** — a LITERAL pattern is matched **exactly**; the only wildcard it supports is the whole name being `*` (meaning every resource). `team-a.*` as a LITERAL pattern matches one topic literally called `team-a.*`.
- 🧠 **Key point / trap:** three ACL facts that recur — **PREFIXED covers future resources**, **DENY always wins**, **default is deny once an authorizer is set**. And a consumer needs `Read` on both the **Topic** and the **Group**.

### Question 24 — Answer: **B**

- **Why correct:** all four pairings are right, and they are right in the way an on-call runbook needs them. `UnderReplicatedPartitions` > 0 = replicas exist but are not all in sync → **redundancy degraded**. `OfflinePartitionsCount` > 0 = no leader can be elected → **availability lost**, the more serious alarm. `ActiveControllerCount` is meaningful only as a **cluster-wide sum**, which must equal 1. `RequestHandlerAvgIdlePercent` below **0.3** means the I/O thread pool is saturated, and the dial is `num.io.threads`.
- **Why the others are wrong:** **A** — swaps the meanings of the two partition metrics, treats `ActiveControllerCount = 2` (split brain) as healthy, and attributes a request-handler metric to the network threads. **C** — `UnderReplicatedPartitions` > 0 does **not** by itself block `acks=all` writes (that is `UnderMinIsrPartitionCount`), offline partitions are not a lag problem, and a **high** idle percentage means the broker has headroom, not that it is overloaded. **D** — URP and offline partitions are different conditions, not two views of one; `ActiveControllerCount` counts **active** controllers (1), not quorum members (3); and the metric measures thread idle time, not disk.
- 🧠 **Key point / trap:** matching questions punish "nearly right" sets — verify **every** pair before choosing. The two that trip people most often are `ActiveControllerCount` (cluster-wide sum = 1, not per broker) and the idle-percent direction (**low** idle = saturated).

### Question 25 — Answer: **D**

- **Why correct:** an oversized record has to pass four independent limits, and missing any one of them breaks the pipeline somewhere else. The broker/topic limit (`message.max.bytes`, default **1048588**, or the topic-level `max.message.bytes`) is what rejected the write. `replica.fetch.max.bytes` (default **1048576**) is the one people forget: if followers cannot fetch a record the leader accepted, the partition can never come back into sync and stays permanently under-replicated. The producer's `max.request.size` and the consumer's `max.partition.fetch.bytes` complete the chain.
- **Why the others are wrong:** **A** — the broker enforces its own ceiling; raising only the client limit reproduces the same `RecordTooLargeException`. **B** — `socket.request.max.bytes` (100 MiB) bounds the size of an entire **request**, not of a record, and the record limit is checked separately. **C** — `log.segment.bytes` is the segment roll size; records are not constrained by it, and raising it to 4 MB+ is unrelated to the failure.
- 🧠 **Key point / trap:** the four-limit chain — **producer → broker/topic → replica fetch → consumer**. `replica.fetch.max.bytes` being left behind is the one that turns a configuration oversight into a durability incident.

### Question 26 — Answer: **A**

- **Why correct:** each Connect worker scans `plugin.path` and builds isolated plugin classloaders **when the worker JVM starts**. Connector and task restarts are logical operations inside the running JVM — they re-instantiate the connector from classes already loaded, so a new JAR on disk is simply never read. Picking up a new plugin version therefore requires restarting the **worker processes**, done as a rolling restart so the cluster keeps running while tasks migrate.
- **Why the others are wrong:** **B** — pause and resume are also logical state transitions inside the same JVM; they reload nothing from disk. **C** — `plugin.path` is a **worker** property; connector configurations cannot add classpath entries. **D** — `connect-configs` stores connector **configurations**, not code; deleting it would destroy every connector definition in the cluster while leaving the classloader exactly as it was.
- 🧠 **Key point / trap:** the operational split — **REST restarts are logical** (connector/task state) and **classloading is a process-lifetime event** (worker restart). The same reasoning explains why adding a brand-new plugin also needs a worker restart.

### Question 27 — Answer: **C**

- **Why correct:** the log message names the cause verbatim — the time between two `poll()` calls exceeded `max.poll.interval.ms`, so the member left the group voluntarily, triggering a rebalance, which pauses consumption and makes lag grow, which makes the next batch even slower. The two levers are both application-side and both cheap: process fewer records per iteration (`max.poll.records`, default **500**) or allow more time per iteration (`max.poll.interval.ms`, default **300000** ms). Low CPU confirms the loop is blocked on something external, not compute-bound.
- **Why the others are wrong:** **A** — adding partitions is a **one-way** change that breaks key-to-partition mapping and does not shorten the time this consumer spends on a single poll batch; the loop would still exceed the interval. **B** — `session.timeout.ms` governs the **heartbeat** clock, and the heartbeat is sent from a background thread that is demonstrably alive; raising it changes nothing here. **D** — more consumers cannot help while the group is rebalancing every few minutes, and if members already equal the partition count the new ones would simply idle.
- 🧠 **Key point / trap:** two independent clocks. A **slow poll loop** breaks `max.poll.interval.ms` (5 minutes); a **dead process** breaks `session.timeout.ms` (45 s). Read the log line to see which clock fired before changing anything.

### Question 28 — Answer: **B**

- **Why correct:** the sizing formula is `throughput × retention × RF × headroom`. Here: 60 MB/s × 86,400 s = **5.18 TB/day**; × 7 days = **36.3 TB** of unique data; × RF 3 = **108.9 TB** actually stored across the cluster; × 1.2 headroom ≈ **131 TB** of raw disk to provision. The tiered-storage remark is the operationally important half of the answer: with `remote.storage.enable`, `local.retention.ms` can hold only hours locally while the topic's full retention lives in object storage, which is how long-retention clusters avoid buying 131 TB of broker disk.
- **Why the others are wrong:** **A** — followers store **full copies**; replication multiplies stored bytes by RF, it does not share segments. **C** — headroom is not optional: compaction, reassignment, a broker failure that concentrates load, and segment-roll timing all need slack, and a disk that reaches 100% takes the log directory offline (see Q10). **D** — same error as A, and it also misstates replication as a network-only cost.
- 🧠 **Key point / trap:** the two sizing formulas to have in muscle memory: **disk = throughput × retention × RF × 1.2** and **partitions = `max(T/P, T/C)`** plus growth. Remember that partition count can be increased but **never** decreased.

### Question 29 — Answer: **A**

- **Why correct:** internal topics do not use the ordinary topic defaults. `__consumer_offsets` is created with **50** partitions and the replication factor from `offsets.topic.replication.factor`, whose default is **3**; `__transaction_state` likewise uses **50** partitions with `transaction.state.log.replication.factor` **3** and `transaction.state.log.min.isr` **2**. On a two-broker cluster the requested RF of 3 cannot be satisfied, which is precisely the `InvalidReplicationFactorException` shown. The fix is to lower those broker configs (to 1 or 2) before the first offset commit.
- **Why the others are wrong:** **B** — the error message itself contradicts this: `num.partitions`/`default.replication.factor` default to 1, so an application topic would never request RF 3. **C** — `__consumer_offsets` is **compacted**, not delete-retained; `offsets.retention.minutes` governs how long offsets of an *empty* group survive and has nothing to do with topic creation. **D** — internal topics are created by the coordinator regardless of `auto.create.topics.enable`, which only controls implicit creation of **client-requested** topics; re-enabling it would not change the replication factor being requested.
- 🧠 **Key point / trap:** this is the number-one reason a single-node or two-node lab "works until someone commits an offset". Every small cluster must lower `offsets.topic.replication.factor`, `transaction.state.log.replication.factor` and `transaction.state.log.min.isr` — and, from 4.2, `share.coordinator.state.topic.replication.factor` too.

### Question 30 — Answer: **D**

- **Why correct:** each requirement maps to a different mechanism, and the answer keeps them separate. In-transit encryption **including inter-broker** means the inter-broker listener itself must be TLS, which is done by mapping listeners to `SSL` in `listener.security.protocol.map` and pointing `inter.broker.listener.name` at that listener — a very common omission that leaves replication traffic in plaintext. Certificate-based client authentication is mTLS, i.e. `ssl.client.auth=required`. And Apache Kafka has **no built-in at-rest encryption**, so that requirement is satisfied outside Kafka with disk or volume encryption.
- **Why the others are wrong:** **A** — TLS protects data **on the wire** only; segments are written to `log.dirs` as plaintext regardless of the listener configuration. Believing otherwise is a genuine audit finding, not just an exam mistake. **B** — GSSAPI is **Kerberos**, a SASL mechanism; certificate authentication is mTLS at the TLS layer, not a SASL mechanism. **C** — mTLS works exactly the same on KRaft clusters; nothing about the metadata layer changes client authentication options.
- 🧠 **Key point / trap:** keep the three layers distinct — **TLS = encryption in transit**, **mTLS/SASL = authentication**, **ACL = authorization** — and remember the fourth item that is *not* Kafka's job at all: **encryption at rest belongs to the disk**.
